## 1. 整体结构

插件系统分三层，**依赖方向单向向下**（架构守卫规则 4 强制 core 不反向依赖上层）：

```
┌─ 界面层 ────────────────────────────────────────────────────────────────┐
│  pages/Board.tsx            挂载插件对话框宿主、注册「画布桥」          │
│  pages/board/contextMenus.tsx  画布空白菜单合并插件注册的项             │
│  components/ui/settings-plugins.tsx   设置面板「插件」页                │
│  components/ui/plugin-dialog-host.tsx 把插件交出的 render 挂成模态框    │
└──────────────────────────┬──────────────────────────────────────────────┘
                           │ store / 桥接
┌─ 宿主层（core）──────────┴──────────────────────────────────────────────┐
│  core/plugin/pluginHost.ts   发现 → 校验 → 激活 → 停用 → 卸载 → 载入    │
│  core/plugin/pluginApi.ts    把宿主能力拼成插件看到的那个 api 对象      │
│  core/plugin/pluginStoreFile.ts  plugins.json 读写（原子写 + 损坏容错） │
│  core/plugin/boardBridge.ts  画布能力注入点（上层实现，插件消费）       │
│  core/plugin/manifest.ts     manifest.json 的 zod 校验与序列化          │
│  core/plugin/{lifecycle,version,pluginText,types}.ts  判定 / 比较 / 文案 / 类型 │
│  core/registry/pluginCenter.ts  注册表 + 归属 + 注销 + 注册表版本号     │
│  core/store/{pluginsStore,pluginUiStore}.ts  列表状态 / 对话框状态      │
└──────────────────────────┬──────────────────────────────────────────────┘
                           │ registerX / activate(api)
┌─ 插件层 ─────────────────┴──────────────────────────────────────────────┐
│  plugins/index.ts         barrel（应用接触插件系统的唯一入口）          │
│  plugins/builtinPlugins.ts  随应用发布的内置插件清单                    │
│  plugins/bootstrap.ts    启动引导（登记 + 初始化）                      │
│  plugins/colorCard/      色卡插件（一个插件一个文件夹）                 │
│  plugins/demo/           示例插件（仅测试调用，不在清单里）             │
└─────────────────────────────────────────────────────────────────────────┘
```

**最关键的一条纪律**：插件**不 import 宿主**。它只拿到宿主在 `activate(api)` 里注入的
`api` 对象。原因是宿主必须知道「哪些注册属于哪个插件」才能实现停用 / 卸载 ——
插件若自己 `import { registerCardType }`，注册表就失去了归属信息。

## 2. 各模块职责

### 2.1 注册表与归属（`core/registry/pluginCenter.ts`）

| 能力 | 职责 |
|---|---|
| `registerCardType` / `registerMenuItem` / `registerCanvasMenuItem` / `registerToolbarItem` / `registerHook` | 五个扩展点的写入端（**保留原有签名不变**，核心与既有测试继续可用） |
| `createPluginApi(pluginId)` | 插件唯一入口：绑定 id 的注册 API，每次注册顺带登记归属 |
| `disposePlugin(pluginId)` | 注册的逆操作：整体回收该插件的注册，返回摘除数量 |
| `registryVersion` / `getRegistryVersion()` | 注册表版本号，任何注册/注销都自增；UI 据此重渲染 |
| `emitHook` / `emitHookTyped` | 触发钩子；单个回调抛错不影响其他回调 |
| `HookPayloadMap` | 7 个钩子的载荷定形（此前是裸 `unknown`，插件只能靠猜） |

### 2.2 宿主编排（`core/plugin/pluginHost.ts`）

把「插件」从一堆文件变成可用能力的编排层，负责五件事，别的模块都不负责：

1. **发现** —— 内置插件（编译期描述符）+ 外部插件（扫描 `%APPDATA%\Mindscape\plugins\`）
2. **校验** —— 外部插件读 `manifest.json` 过 zod
3. **激活** —— 动态 `import`（或直接调用内置 `activate`）→ 注入 `PluginHostApi`
4. **停用** —— 先 `disposePlugin` 回收注册，再让插件 `deactivate` 清理自己的外部资源
5. **卸载** —— 停用 + 递归删除安装目录，**保留插件配置**

磁盘扫描 / 目录删除 / 模块导入 / 读清单全部可在 `PluginHostOptions` 里注入假实现，
因此本模块能在 node 环境完整单测（不读真实磁盘、不起 Tauri）。

### 2.3 插件看到的 API（`core/plugin/pluginApi.ts`）

`buildPluginApi(context)` 把四处能力拼成一个对象：

| 分组 | 能力 | 落点 |
|---|---|---|
| （顶层） | `registerX` 五个注册函数 | `pluginCenter.createPluginApi` |
| `ui` | `openDialog(title, render)` / `closeDialog` | `core/store/pluginUiStore` + `plugin-dialog-host.tsx` |
| `fs` | `writeBytes` / `pickDirectory` | `StorageProvider`（Rust `write_file_bytes`）+ dialog 插件 |
| `board` | `currentSpacePath` / `createCardFromFile` | `core/plugin/boardBridge`（**由 Board 注入实现**） |
| `config` | `getAll` / `set`（浅合并、立即落盘） | `pluginHost` 读写 `plugins.json` |

这一层刻意不做业务判断，只做「把 A 的能力转手给 B」。

### 2.4 状态与界面

| 模块 | 职责 |
|---|---|
| `core/store/pluginsStore.ts` | 宿主列表的**订阅者与转发者**（不复制业务逻辑，避免两处状态打架） |
| `components/ui/settings-plugins.tsx` | 「插件」页主体：列表 / 启停 / 详情 / 卸载 / 重新加载 / 刷新 |
| `components/ui/plugin-list-item.tsx` · `plugin-detail.tsx` | 单行与详情面板（可用性判定来自 `core/plugin/lifecycle.ts`） |
| `core/store/pluginUiStore.ts` + `plugin-dialog-host.tsx` | 「插件交出 render 函数、宿主负责挂载」的对话框通道 |

## 3. 关键实现要点

### 3.1 归属与同一性校验（`disposePlugin` 最容易写错的地方）

停用插件 = 回收它的注册。但注册表是 **Map 单键**：两个插件可能注册同一个 id。
若按 key 直接删，「注销 A」会把 B 后来覆盖上去的定义一起删掉 —— 插件的停用会波及别的插件，
与「插件抛错只影响自己」的设计原则冲突。

因此每条归属记录都带上**注册时交出去的那个对象**（`OwnedRegistration.ref`），
注销前做同一性比较：只有注册表里的当前值仍是它，才允许删除。
`pluginCenter.test.ts` 里有专门用例断言「注销前者返回 0 且 B 的定义完好」。

### 3.2 六态状态机与「失败隔离」

```
discovered ──校验失败──→ invalid          installed ──启用──→ active
     └──校验通过──→ installed                  ↑               │
                                               └───停用── inactive
     任一环节抛错 ──→ error（注册已回收，detail 带中文原因）
```

`enable()` 把 `activate(api)` 包在 try/catch 里：**失败时 `disposePlugin` 回收它半途
注册的内容**，再把状态置为 `error`。用户修好文件后可直接点「重试」（`canEnable` 允许 error）。

### 3.3 内置插件默认启用，外部插件默认停用

- 内置插件是随应用发布的第一方能力，要求用户先去设置页点一次「启用」才能用属于多余的摩擦 ——
  **首次登记时写入 `enabled: true`**（`registerBuiltins` 用 `isFirstSeen` 判断）。
- 已登记过的记录一律尊重用户的选择，所以「用户停用它」不会被下次启动改回去。
- 外部插件是用户从别处拿来的，应先看清来源再启用，保持 `installed`。

### 3.4 画布桥：core 不能 import 上层，就反过来注入

插件要「在画布上加一张卡」，而建卡必须走**画布坐标换算 + 读图片原始尺寸 + 资源表登记 +
`addCards` 命令 + 落盘调度器** —— 这些只活在 `pages/Board.tsx` 的闭包里。
而 core 层不能 import 上层（守卫规则 4），于是反过来：

```
Board 挂载  → setPluginBoardBridge({ currentSpacePath, createCardFromFile })
Board 卸载  → setPluginBoardBridge(null)
```

未注册时（还没打开空间）插件的建卡请求返回 `false`，插件据此给用户一句中文说明，
而不是静默失败。`createCardFromFile` 是**异步**的 —— 上面那五步一步都不能省，
否则卡片没有正确的宽高比、图片显示不出来。

### 3.5 插件对话框：宿主只认一个 render 函数

插件需要自己的输入界面，但它既不在 React 树里，也不该 import 宿主的弹窗组件
（否则插件代码就散到宿主里了）。约定：

```
插件 activate(api) → api.ui.openDialog('新建色卡', () => <ColorCardDialog api={api} />)
宿主 <PluginDialogHost />（挂在 Board）订阅 pluginUiStore 并渲染
```

于是**插件 UI 的全部代码待在插件自己的文件夹里**，宿主完全不认识「色卡」这个概念。

### 3.6 色卡 PNG：零 Rust 改动

Tauri 侧没有图像编码依赖（17.1 依赖清单锁定，加 `image` crate 属于清单外新增），
而 WebView2 自带 Canvas 2D —— 画 + `toBlob('image/png')` 就能拿到标准 PNG，
落盘复用已有的 `write_file_bytes` 命令。

可测性上做了一处关键设计：**画布工厂可注入**。本项目不引入 jsdom（用户裁决），
所以测试注入一块记录绘制指令的假画布，把「底色铺满 / 标注文字 / 尺寸正确 / 文字色可读」
在 node 环境钉死，而不必渲染真实像素。

### 3.7 「文件是产物，卡片是视图」

色卡插件的产物是**存到指定文件夹的 PNG**；在画布上建卡只是顺手的便利。由此推出两条规则：

1. 输出文件夹**不在当前空间内**不是错误，而是「只写文件」——结果里带中文原因，界面如实告知。
2. 建卡**不进撤销栈**（`CreateCardInput.undoable: false`）。原因很硬：PNG 是插件现画的二进制，
   没有「源文件」可供 redo 重新复制；若塞进 `addCards` 命令，一次「撤销」就会删掉用户刚要的
   色卡文件，而 redo 再也造不回来。卡片本身仍可被正常移除（走卡片自己的移除命令）。

### 3.8 落盘与容错

- 状态文件：`%APPDATA%\Mindscape\plugins.json`，**原子写**（`.tmp` + rename），
  与 `spaces.json` 同一套策略。
- 损坏容错：解析失败 → 备份 `plugins.json.bak` → 以空列表启动，**原文件不动**，
  并把中文原因交给设置页展示（`lastError`）。
- **插件配置不随卸载删除**：卸载只删安装目录并把 `dir` 置空，`config` 原样保留 ——
  与「卡片 meta 不因卸载而蒸发」同一约定。
- 插件抛错只影响自己：`emitHook` 与 `enable` 都逐插件隔离。

### 3.9 启动引导：不阻塞首帧

`main.tsx` 里 `void bootstrapPlugins()` —— 刻意**不 await**：`init()` 有磁盘 I/O，
阻塞首帧去等它只是让启动变慢；而内置插件只注册画布菜单项，菜单是**右键时才查表组装**的
（`pages/board/contextMenus.tsx`），晚一拍注册不会漏项。
将来若有插件要注册**卡片类型**（渲染时查表，必须首帧前就位），把 `await` 加回来即可。

异常兜底：插件系统坏掉**绝不能**让应用起不来 —— `bootstrapPlugins` 吞掉异常只记日志。

### 3.10 守卫与棘轮

- **规则 3**：色板预设的 hex 是「给用户挑的数据」，登记在 `RAW_COLOR_ALLOWLIST`；
  PNG 里的标注文字色刻意用 CSS 关键词 `black` / `white` 而不是 hex，因此无需豁免。
- **规则 6**：新模块都带同名测试；只有渲染层（`dialog.tsx`）与 barrel（`index.ts`）
  进 `UNTESTED_ALLOWLIST` 并写明原因。
- **规则 1**：`Board.tsx` 实际 2049 行，阈值 2080，余量 31 行预留给 7 个钩子的埋点；
  若埋点后还要加东西，先按方案 §7 再拆一块出去，而不是直接抬高阈值。

### 3.11 通用悬停标记：核心不认识插件

色卡要「默认不显示色号、悬停才显示」，而渲染层在 `core/registry/cardTypes.ts` ——
如果核心去读 `meta['mindscape.color-card'].color`，就等于 **core 认识了具体插件**，
违反 3.1 那条铁律的同一精神（归属必须可回收，宿主不该知道插件的存在）。

于是把它做成一格**通用扩展位**：`card.meta.hoverLabel`（`core/board/cardMeta.ts`）。
核心只回答「这张卡有没有一个悬停标记」，标记是什么、谁写的，与核心无关。
色卡插件把色号写进去，任何插件都能用同一格。

显示与否走**纯 CSS**（`group-hover`，`group` 挂在 `canvas/Card.tsx` 的卡片根元素上），
**不进 React state** —— 悬停是高频事件，进 state 会触发重渲染，撞 17.3 的红线。
另一个细节：只有悬浮标记、没有备注 / 标签时，**整条外挂层**随悬停淡入
（否则卡片上方会留一个空胶囊），并加 `pointer-events-none` 不抢画布的指针事件。

## 4. 色卡插件的数据流

```
画布空白右键
  └→ 「新建色卡…」            plugins/colorCard/index.tsx（registerCanvasMenuItem）
       └→ api.ui.openDialog('新建色卡', () => <ColorCardDialog/>)
            ├→ 参数初值        options.optionsFromConfig(api.config.getAll(), 当前空间)
            ├→ 用户选色        预设色板 / 系统取色器 / 手输（normalizeHex）
            ├→ 用户选尺寸      比例（1:1 / 16:9 / 9:16）× 长边像素（512…2560）
            │                  options.sizeForRatio / sizeForLongEdge
            ├→ 输出文件夹      api.fs.pickDirectory()
            └→ 点「生成并保存」  save.saveColorCard(...)
                 ├→ 校验        normalizeHex（**归一化之前**校验，防错字被静默换成默认色）
                 ├→ 画图        png.renderColorCardPng → Canvas 2D → toBlob → Uint8Array
                 │              showHex **默认 false**：色号不画进图（2026-09-14 用户裁决）
                 ├→ 写盘        api.fs.writeBytes → Rust write_file_bytes（重名自动加 _1）
                 ├→ 记住参数    api.config.set → plugins.json
                 └→ 可选建卡    api.board.createCardFromFile（仅当输出目录在空间内）
                                meta = { 'mindscape.color-card': {…}, hoverLabel: 色号 }
                                undoable: false
                                      ↓
                        画布上悬停该色卡 → 图片区域外的左上角淡入显示色号
                        （core/registry/cardTypes.ts 的 hoverLabelChip，纯 CSS group-hover）
```

## 5. 新增一个插件怎么做

> **本节的展开版（含 API 全量参考、清单契约、排错对照表、可复制示例）见
> `docs/插件开发指南.md`** —— 要动手写插件看那一份，这一节只留最短路径。

1. 建目录 `src/plugins/<插件名>/`，按需放：`index.tsx`（元信息 + `activate`）、
   `text.ts`（文案）、其余纯逻辑模块（**每个都要有同名测试**）、`*.tsx`（界面）。
2. 导出 `BuiltinPluginDescriptor`（`manifest` + `activate(api)` + 可选 `deactivate`）。
3. 登记到 `src/plugins/builtinPlugins.ts` 的数组里（一行）。
4. 只通过 `api` 使用宿主能力；**不 import 宿主的注册函数**，也不 import 别的插件。
5. 若需要新能力：先在 `core/plugin/types.ts` 的 `PluginHostApi` 上加，再在
   `pluginApi.ts` 里接线；需要界面就交 render 函数，需要画布就扩 `boardBridge`。
6. 门禁：`pnpm typecheck && pnpm lint && pnpm test && pnpm build`。
7. 外部插件（不进仓库）用同一套形状：`manifest.json` + `index.js` 导出 `activate`，
   放进 `%APPDATA%\Mindscape\plugins\<id>\`，在设置页点「刷新」即可发现。

## 6. 已知限制（有意取舍）

- **色卡卡片在重新打开空间后是 `image` 类型**。原因：文件扫描按扩展名分类，
  PNG 必然被识别为图片卡。插件没有为色卡注册独立的卡片类型，正是为了避免
  「只在本次会话里存在、重开空间就变成图片卡」的不一致观感 —— 现在两种情形观感一致，
  且 `card.meta['mindscape.color-card']` 仍然保留下来。
- **插件停用不回收已产生的卡片 / 文件**。停用只回收注册（菜单项消失），
  已建卡片是用户数据，与插件状态无关。
- **外部插件动态加载走 `convertFileSrc` + `import(/* @vite-ignore */)`**：
  需要 Tauri 的 `csp=null` 与 `assetProtocol.scope`（都已具备，接入零配置改动）。
  插件是多文件时同样可行。
- **7 个生命周期钩子的生产埋点尚未接线**（`emitHook` 目前只有测试在调），
  `HookPayloadMap` 已把载荷定形，埋点处用 `emitHookTyped` 即可。
- **`registerToolbarItem` 目前没有渲染端**：顶部图标工具栏已在重构中移除
  （撤销 / 重做 / 复制 / 粘贴 / 删除 / 恢复并入右键菜单），`core/registry/toolbar.ts`
  只被自己的测试引用。注册了不会有界面变化，是**为将来预留的通道**。
- **色号悬停标记只对「由插件建卡」的色卡生效**：`meta.hoverLabel` 由插件在建卡时写入，
  用户后来手动拖进来的同名 PNG 没有这格 meta，自然没有悬停色号
  （此时也读不出色号 —— 默认不画进图）。
- **`plugins.json` 的 `version` 字段有、迁移函数没有**。在插件配置结构变更前补上。
