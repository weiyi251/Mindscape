# Mindscape 代码审查报告（插件功能开发前）

> 审查日期：2026-09-13
> 审查范围：`src/` 全部 161 个 `.ts/.tsx` 文件（28,459 行）、`src-tauri/src/`、`docs/`、根级配置与文档
> 审查方式：静态引用图扫描（`.workbuddy/audit-unused.mjs`）、跨模块同名符号比对、逐模块人工阅读、架构守卫规则核对
> **本报告只做结论与建议，未修改任何代码。**

## 0. 结论摘要

整体质量**好于一般项目**：分层（`core` / `canvas` / `components` / `pages`）清楚，纯逻辑与渲染分离得相当彻底，已有 6 条自动化架构守卫，测试 834 例全绿，模块级中文说明齐全。

真正需要处理的问题是**三类**，按优先级：

| 级别 | 问题 | 影响 | 条目 |
|---|---|---|---|
| **P0** | 插件脚手架**存在但未接线**（无引导入口、钩子从不触发、工具栏通道悬空、菜单模型两套） | 直接阻塞插件功能开发 | §5.1–5.5 |
| **P0** | 架构守卫规则 4 是**白名单漏洞**（denylist 写法） | 新增顶层目录即可绕过分层约束，插件期最容易踩 | §5.7 |
| **P1** | `core/` 内混入 **React 渲染实现**（`cardTypes.ts` 457 行中约 300 行是 JSX），且 registry 反向依赖 `commands/impl` 与 `board/` | 层次倒置，插件作者会照抄错误范式 | §3.2、§4.2 |
| **P1** | 真实重复代码 7 处（`unionRects` / `safeZoom` / `pad2` / `toMessage` / 矩形类型 ×4 / 缩放适配内核 / 两套弹窗） | 修改时需要同步多处，易漂移 | §2 |
| **P2** | 目录与文件错位 8 处（`core/utils` 杂物袋、`components/ui` 混装业务组件、偏好键散落且命名不统一等） | 新人定位成本高，插件扩展点不清晰 | §4 |
| **P2** | 过时注释与文档 6 处；真正可删的死代码仅 2 个图标 + 1 份过时计划文档 | 误导后续开发 | §1 |
| — | `package.json` 依赖**无真正未使用项** | — | §1.4 |

> ⚠️ **必须先明确**：`pluginCenter` / `toolbar.ts` / `actionRegistry` / `menu-list.tsx` / `plugins/*` 是**用户裁决（2026-09-13）要求一律保留的插件预留层**，本次审查**不建议删除其中任何一项**。它们是插件开发的地基，问题在于"没接通"，不在"没用"。

## 3. 职责与分层问题

### 3.1 已做对的（不建议动）

- **纯逻辑 / 渲染分离彻底**：`canvas/interaction/*.ts` 全是无 DOM 的控制器与几何纯函数，配同名测试；`Canvas.tsx` 只做接线。这是全项目最健康的部分。
- **主题是正确分层**：`core/utils/theme.ts`（纯函数）+ `core/hooks/useTheme.ts`（React 胶水），非重复实现。
- **Canvas 坐标 / 视口 / 拖拽**三套控制器各自独立，未互相 import。

### 3.2 层次倒置（**P1，插件开发前应修**）

**问题**：`core/registry/cardTypes.ts`（457 行）同时承担 4 类职责，其中两类越界：

```
38-52   元数据类型（LABELS / DEFAULT_SIZE）              ← 本层职责 ✓
59-243  11 个 JSX 渲染辅助（miniIcon / noteIcon / tagIcon /
        noteBar / tagBar / imageOverlay / shell）          ← 渲染层职责 ✗
278-383 3 个渲染实现（renderImage / renderFile / renderNote）← 渲染层职责 ✗
384-457 查表 + 插件兜底 + 聚合                          ← 本层职责 ✓
```

**并且**它 import 了这些东西（第 24–31 行）：

```ts
import { toAssetUrl } from '@/core/utils/media'          // 平台桥
import { getCardOriginalPath } from '@/core/board/cardAssets'
import { tagsOfMeta } from '@/core/commands/impl/setCardMeta'   // ← registry 依赖命令层
```

即：**`registry/`（配置层）反向依赖 `commands/impl/` 与 `board/`（业务层）**，方向错了。`core` 里出现 `createElement` / JSX 也让"core = 无 UI 域层"的约定失效。

**建议拆法**：

```
core/registry/cardTypes.ts      保留 ≈120 行：LABELS / DEFAULT_SIZE / CORE_CARD_TYPE_DEFS
                                / getCardTypeDef / listCardTypes / renderCard 转发
canvas/cardRender/
    shell.tsx                   共享外壳 + 视觉常量（CARD_VISUAL_DEFAULT / NOTE_VISUAL）
    badge.tsx                   miniIcon / noteIcon / tagIcon
    overlay.tsx                 noteBar / tagBar / imageOverlay
    image.tsx  file.tsx  note.tsx
```

**为什么插件开发前做**：`cardTypes.ts` 是插件作者的**唯一范例**（`demoPlugin.ts` 的色卡就是照它写的）。现在范例是"在 core 里 import 命令层写 JSX"，插件作者会照抄，把倒置扩散到每个插件里。

**附带修**：`tagsOfMeta` / `metaWithTags` 是纯数据读写，却住在命令文件 `core/commands/impl/setCardMeta.ts` 里 → 移到 `core/board/cardMeta.ts`，让 `cardTypes` 不再依赖命令层。

## 5. 插件开发前的潜在问题（**本报告重点**）

> 一句话：**插件接口写好了，但没有任何东西会调用它。** 下面 11 条按"必须解决 / 应当解决 / 需用户裁决"分组。

### 必须解决（否则插件功能不可用）

#### 5.1 没有插件引导入口
- **证据**：`src/main.tsx` 与 `src/App.tsx` 均未 import `src/plugins/index.ts`；全项目**没有任何生产代码**调用 `registerDemoPlugin()` 或 `registerCardType/registerMenuItem/registerToolbarItem/registerHook`。`plugins/index.ts` 内容为 `export {}`。
- **后果**：插件永远不会被加载。
- **建议**：新增 `src/app/bootstrapPlugins.ts`，在 `main.tsx` 渲染前（**早于首帧**，避免卡片首渲染时类型还没注册）调用一次；`plugins/index.ts` 改为导出插件清单数组，由 bootstrap 遍历注册。
- **注意**：必须保证"注册早于第一次渲染"，否则 `getCardTypeDef` 会因为类型未注册而把插件卡片渲染成兜底样式。

#### 5.2 生命周期钩子从不触发（7 种全部）
- **证据**：`emitHook()` 在生产代码中**零调用**（仅 `pluginCenter.test.ts` / `demoPlugin.test.ts` 调用）。
- **后果**：`registerHook` 是空承诺，插件的"监听卡片移动/空间打开"等能力完全无效。
- **建议**：在 7 个点接线 —— `cardSelected` / `cardMoved` / `cardCreated` / `cardRemoved` / `partitionRenamed` / `spaceOpened` / `spaceClosed`。其中 `cardMoved` 属高频路径（拖动中每帧触发），**必须定义"只在落点提交时 emit 一次"**，否则会拖垮手感（与 17.3 同精神）。
- **同时**：`HookFn = (payload: unknown) => void` 需为每个 `HookName` 定形（建议 `core/plugin/payloads.ts` 导出 `HookPayloadMap`），否则插件作者不知道能拿到什么。

#### 5.3 工具栏通道悬空
- **证据**：`registerToolbarItem` 只被 `core/registry/toolbar.ts` 消费；而 `toolbar.ts` 仅被自己的测试引用，**真实工具栏 `icon-toolbar.tsx` 已于 2026-09-13 删除**（功能并入右键菜单）。
- **后果**：插件注册的工具栏按钮无处显示。
- **三选一（需用户裁决）**：
  1. 重建一个读 `listToolbarItems()` 的宿主（例如顶栏溢出菜单 / 命令面板）；
  2. 把"工具栏项"重定向为"命令面板项"（与键盘派发共用）；
  3. 明确废弃该通道 —— 但按裁决 8，**代码保留**，仅在文档中标注"未接线"。

#### 5.4 菜单模型两套 + 第三条渲染路径
- **证据**：
  - `MenuItem`（`pluginCenter.ts:73`）：只有 `id / label / appliesTo / action`。
  - `ContextMenuItemData`（`context-menu.tsx`）：有 `id / label / icon / separatorBefore / danger / run`，且 Board 还额外拼快捷键标签（`withShortcutLabel`）。
  - `MenuListEntry`（`menu-list.tsx:25`）：只有 `id / label / action`，**且这个组件在生产代码里零引用**（Board 直接用 `context-menu.tsx`）。
- **后果**：插件菜单项**能显示**（`buildCardMenuFor` 已合并插件项 ✓），但**无法带图标 / 快捷键 / 禁用态**；而 `menu-list.tsx` 是个能力更弱的平行渲染器。
- **建议**：`MenuItem` **只增不改**地加 `icon?` / `shortcut?` / `disabled?` / `separatorBefore?`，并在 Board 的映射处透传；`menu-list.tsx` 保留（裁决 8）但在文件头明确标注"备用/示例渲染器，生产路径是 `context-menu.tsx`"。

#### 5.5 动作模型不统一
- **证据**：核心菜单走 `runAction(id, label, ctx)` + `registerAction`（Board 在 `useEffect` 里登记 11 个动作）；插件菜单走 `item.action(ctx)` **直接闭包**。
- **后果**：插件动作无法被快捷键 / 命令面板 / `hasAction` 置灰机制复用；`actionRegistry` 的价值对插件不开放。
- **建议**：让插件菜单项也推荐"`action` 内部调 `runAction`"，或提供 `registerPluginAction()` 便利函数，统一到 id-注册表模型。

### 应当解决（现在不做、插件期会加倍**

#### 5.6 插件数据的版本与迁移
- 现状：`card.meta` / `partition.meta` / `layout.extensions` 都是 `z.record(z.unknown())`（自由槽位 ✓），顶层有 `version` + `DATA_VERSION = 1`，但**读到更高版本就整体只读，没有按插件的迁移钩子**。
- 风险：插件一旦改自己的 meta 结构，老数据没有升级入口。
- 建议：约定插件自治版本位（如 `meta.__v`）与 `migrateMeta(meta)` 钩子；**不要**用顶层 `DATA_VERSION` 表达插件结构（它管的是核心数据结构）。

#### 5.7 架构守卫规则 4 是白名单漏洞（**必须补**）
- 现状：`CORE_FORBIDDEN_IMPORT = /from\s+'@\/(?:canvas|pages|components|plugins|lib)\//` —— 这是**黑名单**。
- 后果：本报告 §4.2 建议新增 `src/platform/`，`core/` 里 `import '@/platform/asset'` 就**不会被拦**；任何未来新顶层目录同理。插件期目录会变多，这个洞会张开。
- 建议：**反向改成白名单** —— `core/**` 只允许 import `@/core/**`，其他一律报错（并同步更新 §4.2 的迁移：`core/utils/media.ts` → `platform/asset.ts` 时，`cardTypes.ts` 的引用也要跟着改，因为白名单会拦住它）。

#### 5.8 插件缺少可移植性约束
- 现状：`src/plugins/**` 只受"规则 6（要有同名测试）"约束，可以随意 import `pages/Board`、`canvas/*`。
- 风险：插件与核心深度耦合后无法单独分发/禁用。
- 建议：新增守卫"`src/plugins/**` 只允许 import `@/core/plugin/*`（接口）与 `@/core/types`（数据契约）+ React"，从机制上保证插件只通过接口与核心交互。

#### 5.9 HMR 重复注册与注销能力
- 现状：`pluginCenter` 重复注册是"覆盖 + `console.warn`"（开发期友好 ✓）；但 `registerHook` 用 `Set<HookFn>` 去重，**HMR 每次生成新的函数引用**，旧引用不会被移除 → 钩子会随保存次数线性叠加；`resetPluginCenter()` 只标注"仅供测试"。
- 建议：提供 `disposePlugin(pluginId)`：按插件 id 批量注销其卡型 / 菜单 / 工具栏 / 钩子；注册时记录归属插件 id。

#### 5.10 大文件棘轮与插件接线直接冲突
- 现状：守卫规则 1 要求 `Board.tsx ≤ 2117`、`Canvas.tsx ≤ 1192`（当前 2093 / 1192 —— Canvas **顶死**，Board 只剩 24 行余量）。
- 后果：**第一个插件接线就会撞红线**（每次 emitHook 都要往 Board 加行）。
- 建议：先把 §4.2 的 `pages/board/` 三个 hook 拆出来（净减行），再开始插件功能。这是硬性前置。

#### 5.11 测试与守卫的薄点会被插件放大
- `UNTESTED_ALLOWLIST` 中仍有 **14 条"待补测试（存量）"**：`canvas/viewportSnapshot.ts`、`core/board/ingest.ts`、`core/commands/impl/{connections,movePartitions,resizeCards,setCardMeta,setCardNote,setCardsZIndex,setPartitionColor}.ts`、`core/commands/types.ts`、`core/hooks/useTheme.ts`、`core/registry/actionRegistry.ts`、`core/storage/StorageProvider.ts`、`core/utils/media.ts`。
- 其中 `actionRegistry`（插件动作分发）与 `media`（插件渲染图片）**正好落在插件路径上**，建议插件开发前补齐这两项。
- 另：用户裁决 4 不引入 jsdom → 插件的**渲染函数无法单测**（`registerCardType` 的 `render` 只能靠无头浏览器验证）。这个约束要在插件开发规范里写清，避免后续为测插件而破例引入 jsdom。

### 需用户裁决

#### 5.12 插件来源与分发方式（计划书未明确 → **应停下提问**）
- 编译期内置（打进 bundle）？还是运行期扫描 `<dataDir>/plugins/` 目录加载？
- 前者简单，后者需要新的 Rust 命令 + 动态模块加载（Tauri 下 WebView 无法直接执行外部 JS，需评估）。
- **这决定了 5.1 bootstrap 的写法与 5.7 守卫的边界**，建议先定方向再动手。

## 7. 一句话总结

**代码本身是干净的，问题集中在"插件地基已浇好但没接钢筋"。** 建议顺序：先做批次 1–2（清死代码 + 去重，收益立竿见影且零风险），再做批次 3（目录归位 + **修补守卫规则 4 的黑名单漏洞**），然后做批次 4（拆 Board/Canvas 腾出棘轮空间），最后才进批次 5 接插件。其中 **§5.12（插件是编译期内置还是运行期加载）与 §5.3（工具栏通道去留）需要你先裁决**，这两项决定后续接线怎么写。
