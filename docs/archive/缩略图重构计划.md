## 二、现状链路（分析结论，重构依据）

### 2.1 生成链路（将被下线/改造）

| 环节 | 位置 | 现状 |
|---|---|---|
| Rust 生成命令 | `src-tauri/src/commands/thumbnail.rs` `make_thumbnail` | 原图完整解码 → 长边 800px → **无损 WebP** 写入 `<空间>\.mindscape\thumbnails\{hash}.webp`；hash=FNV-1a(相对路径+mtime) |
| 批量调度 | `src/core/board/thumbnails.ts` `collectThumbnails` | 6 路并发；provider 未实现时静默返回空 |
| 调用点①②③ | `boardStore.ts:566`（loadSpace）/ `:484`（loadRemovedView）/ `restoreCards.ts:142` | 进空间 / 已移除视图 / 恢复卡片时批量生成 |
| 调用点④ | `fs_ops.rs:311` `copy_image_with_thumbnail`（`Board.tsx:596、768` 调用） | 拖入/粘贴图片时复制文件并顺带生成缩略图 |

### 2.2 加载链路（大部分保留）

1. `registerCardAssets`（`cardAssets.ts`）把 `thumbnailPath`/`originalPath` 写入模块级 Map（不落盘、写入须早于 `boardStore.set({cards})`）。
2. `cardTypes.ts` `renderImage`：`<img src=缩略图>` + `data-original-url=原图`，URL 经 `toAssetUrl`（assetProtocol）。
3. `lazyOriginal.ts`：按 zoom/offset 反算可见矩形 → 可见且未升级的卡片直写 `img.src` 为原图（单向升级、不触发 React）。

### 2.3 关键既有能力（方案 A 的可行性基础）

- **卡片宽高比不依赖缩略图**：Rust 端已有 `read_image_size`（`system.rs:32`，只读图头不解码全图），`Board.tsx:504` 已在用。
- **懒加载机制现成**：`lazyOriginal` 的「仅可见时写 src」可直接复用——初始 src 置空走占位，可见时写原图，视口外图片完全不解码（规避 17.11 反模式 9）。
- **存储暴涨根因**：`image` crate 只支持无损 WebP 编码，照片类缩略图体积与原图同量级——去掉生成即彻底解决。

### 3.3 回退策略

1. **代码层**：`make_thumbnail` 与 `thumbnails.ts` 全程保留；建议 `core/board/thumbnails.ts` 顶部加 `THUMBNAIL_MODE: 'original' | 'legacy-webp'` 常量开关，`loadSpace` 按开关分流——回退只改一个常量；git 单独成 commit 可整体 revert。
2. **数据层**：存量 `thumbnails/` 目录在用户确认清理前原样保留；即使清理后回退，`make_thumbnail` 会按 hash 重新生成，无永久损失。
3. **layout.json 零影响**：本重构不触碰任何落盘数据（资源路径本就不落盘），回退无数据迁移。

## 五、风险清单与缓解

| # | 风险 | 缓解 |
|---|---|---|
| 1 | 大图同屏解码内存/帧率（24MP ≈ 92MB/张解码峰值） | `lazyOriginal` 保证视口外零解码；S5 用真实素材实测帧率；若不达标再评估「大图缩略图外移缓存目录」的渐进增强（方案 C 地基已在初版论证） |
| 2 | 大原图首次显示「空白→出图」跳变 | 占位底色保留 + `decoding:async`；可加淡入过渡（`transition-opacity` 已有底子） |
| 3 | EXIF 方向：浏览器按 EXIF 渲染原图，而旧缩略图按 `image` crate 解码像素（不自动应用 EXIF）→ 切换后竖拍图显示方向可能改变；且卡片宽高比按传感器尺寸计算可能与显示比例不符 | S5 实测竖拍样本；必要时 Rust 侧读 EXIF 修正 `read_image_size` 返回值（`image` crate 0.25 不自动应用，需验证） |
| 4 | 特殊图片格式（CMYK JPEG、16-bit PNG、动图 GIF/WebP）在 WebView 的解码兼容性 | WebView2（Chromium）解码能力远强于 `image` crate，理论风险低于现状；S5 抽样验证 |
| 5 | 已移除视图 / 恢复卡片等冷路径遗漏 | S1 一并切换并保留原测试守护（`restoreCards.test.ts` 等） |
